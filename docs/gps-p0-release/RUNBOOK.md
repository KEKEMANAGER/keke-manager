# GPS P0 — Production-ში გაშვების და დაბრუნების გეგმა

ეს გეგმა სრულდება მხოლოდ აკაკის ცალკე, ახალი თანხმობის შემდეგ. თითოეული ფაილი ერთ
ტრანზაქციად ეშვება:

- ჯერ ამოწმებს, რომ Production ისეთივეა, როგორიც 2026-11-04-ის backup-ში;
- ბოლოს ამოწმებს შედეგს.

თუ რომელიმე შემოწმება ვერ გაიარა, ყველაფერი უკან ბრუნდება და არაფერი იცვლება
(შეცდომის ბოლოს წერია „- stop“). არსებულ ჩანაწერებს (ჯავშნები, მდებარეობები,
მარშრუტები, მგზავრის ნიშნულები, ტურის დღეები) არცერთი ფაილი არ ცვლის.

ფაილები აწყობილია `bash docs/gps-p0-release/build.sh`-ით. ხელით არ შეიცვალოს.

   GPS ცხრილები, წესები, ფუნქციები და cron. დაშიფრული ასლი ინახება იმავე ადგილას:
   `D:\KEKE-BACKUPS\`.
2. **დრო:** ღამე ან დილით ადრე (თბილისით 01:00–06:00), როცა მიმდინარე ტური ცოტაა.
3. **წაკითხვები** (მხოლოდ კითხულობს, არაფერს ცვლის):
   - მიმდინარე ტურები:
     `select id, date_display, updated_at from public.bookings where status = 'in_progress' order by date_display;`
     დიდი ხნის წინ დაწყებული და დაუხურავი ტური ჯერ KEKE-მ დახუროს. ნაბიჯი 2-ის
     დროს მიმდინარე ტურებისთვის „დაწყების დრო“ გაშვების მომენტი ხდება: ის წერტილები,
     რომლებიც ტელეფონმა მანამდე ინტერნეტის გარეშე დააგროვა, აღარ შეინახება.
   - მარშრუტის ჩანაწერების რაოდენობა:
     `select count(*) from public.driver_location_trail;`
     2026-11-04-ს იყო 0. თუ ახლა 0 არ არის, ეს წერტილები ნაბიჯი 2-ის შემდეგ მხოლოდ
     მძღოლს დარჩება, რადგან მათი დროის შემოწმება შეუძლებელია. გაგრძელებამდე აკაკის
     ეცნობოს.
   - კოლონის კოორდინატორი ჯავშნები, რომლებზეც მძღოლია მითითებული:
     `select count(*) from public.bookings where is_group_master and driver_id is not null;`
     ეს მხოლოდ ინფორმაციაა (იხ. „გადაწყვეტილებები“, პუნქტი 2).
4. **აპის ახალი ვერსია (OTA) ჯერ არ ეშვება.** სერვერი ძველ აპებსაც იცავს; OTA ცალკე
   ნაბიჯია (ნაბიჯი 6).

ითვლება.

## 4. შემოწმება Production-ში, ცვლილების გარეშე

`90_smoke_gps_p0.sql` ქმნის დროებით კომპანიას, მძღოლს და ადმინს და ტურს თავიდან
ბოლომდე გაატარებს. ბოლოს ყველაფერი ROLLBACK-ით ქრება და არაფერი იგზავნება.

**სწორი შედეგი:** `ALL SMOKE CHECKS PASSED` (22 შემოწმება).

**შენიშვნა:** მარშრუტის id-ების მთვლელი რამდენიმე ერთეულით წინ წავა, რადგან Postgres-ის
sequence ROLLBACK-ით არ ბრუნდება. ეს უვნებელია (იზოლირებულ ტესტში: 4).

## 5. დაკვირვება (30 წუთი, შემდეგ ყოველდღე ერთი კვირა)

**რა გამოტოვა ან მხოლოდ მძღოლს დაუტოვა სერვერმა, დღეების მიხედვით:**

`select day, kind, sum(n) as n, count(*) as drivers from public.gps_skip_counts group by day, kind order by day desc, kind;`

| kind | რას ნიშნავს |
|---|---|
| `background_position` | ძველი აპის ფონური მდებარეობა ტურის შემდეგ. მოსალოდნელია. |
| `road_point` | გამოტოვებული წერტილი. |
| `road_point_unchecked` | შენახულია მხოლოდ მძღოლისთვის. |
| `road_point_error` | უნდა იყოს 0. |

**გაჩერება და გამოკვლევა:**
- `road_point`-ის ან `road_point_unchecked`-ის ნახტომი (ასობით დღეში), როცა ტურები
  ჩვეულებრივ მიდის;
- `road_point_error`-ის ნებისმიერი მნიშვნელობა.

**cron-ის მუშაობა:**

`select jobname, status, start_time from cron.job_run_details d join cron.job j using (jobid) where jobname in ('gps-tidy-pins', 'watch-trip-gps') order by start_time desc limit 10;`

ორივე უნდა იყოს `succeeded`. Postgres-ის ლოგში `watch_trip_gps: a trip was skipped` არ
უნდა ჩანდეს.

**პირველი გასუფთავების შემდეგ:** `select count(*) from public.driver_locations;`.
დარჩება მხოლოდ მიმდინარე ტურის მძღოლები და ბოლო 15 წუთის ღია ეკრანები.

**რეალური მოწყობილობით (ცალკე, აუცილებელია):**
- კომპანიის ანგარიშით მიმდინარე ტურზე მძღოლი ჩანს; ტურის დასრულების შემდეგ აღარ
  ჩანს. ფლოტის მფლობელსა და ადმინთან იგივე უნდა იყოს.
- მრავალდღიანი ტური: მეორე დღესაც მოდის გაღვიძება და შეტყობინება.
- ტელეფონი სწორი საათით: დასრულებული ტურის მარშრუტი კომპანიას უჩანს.

**წაშლილი პინები** საჭიროებისას ბრუნდება backup-ის `03_data.sql`-ით:

თუ undo ფაილები ვერ გაეშვება, backup-ის `02_rules.sql` GPS ცხრილების წესებს აღადგენს.
