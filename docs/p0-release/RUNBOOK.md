## 2. Safety net

1. **Supabase daily physical backups** (Pro plan): 7 days kept, latest
   31 Oct 03:24:38 UTC, restorable in place or to a new project from the
   dashboard. Point-in-time recovery is **off** (paid add-on) — a full restore
   would lose what was written after the last daily backup, so it is the last
   resort only.
2. **Same-database snapshot** `backup_p0_20261031`, taken 31 Oct 17:38:13 UTC:
   all 37 public tables (5,116 rows) + `_ddl` (1,177 definitions: functions,
   triggers incl. auth/storage, policies incl. storage, indexes, constraints,
   columns, grants, cron jobs) + `_manifest` (rows and md5 per table).
   Verified: 37/37 copies equal to the source; restore drill 37/37
   byte-identical into tables shaped like today's live ones; no API role can
   reach it; no new security advisor finding. Take a fresh one on the day
   (`sql/01_backup_snapshot.sql`, new date) and verify it (`sql/02_verify_backup.sql`).
3. **Every step is one guarded transaction** (generated by
   `tools/build_release_sql.py`, rehearsed by `tools/rehearse_release.sh`). It
   commits only if: the lock comes within 5 s; the database is in the expected
   state; the functions it replaces are exactly the rehearsed versions (md5);
   no existing row of any public table changed (P0-4 may close legacy unsent
   pushes — 0 such rows today); the functions it leaves behind are exactly the
   rehearsed versions. Otherwise it rolls back and nothing changes.
4. **Undo per step**, in reverse order (`rollback/50 … 10`), with the same
   guards; rehearsed: all five undone back to the exact pre-P0 fingerprints,
   then applied again.

## 5. Stop conditions and rollback

Stop and do not continue if: a step does not answer "applied"; a check or a
smoke row fails; a cron job fails after a step; API errors rise; anyone
reports a problem with a booking.

- **Undo a database step**: run `rollback/<n>0_undo_*.sql` for the last
  applied step, then the one before, … (reverse order; each refuses if a later
  step is still in place). Rehearsed for all five. Rows written meanwhile in
  tables the step created (`booking_driver_declines`, `push_tokens`) go with
  them; every other row stays. The app keeps working (fallbacks).
- **Edge Function**: redeploy v7 = `git show 5d3bcca:supabase/functions/booking-reminders/index.ts`.
- **Website**: Cloudflare → Pages → kekemanager → Deployments → roll back to
  the `5d3bcca` deployment (or push master back — only with approval).
- **Phones**: `eas update:republish --group cb588740-2f98-4d74-b438-35bd59a0343c`
  (the 30 Oct update) on channel production.
- **Rows changed by mistake**: `sql/03_restore_rows_from_snapshot.sql`
  (template: preview, then restore one table's rows from the snapshot).
- **Last resort**: dashboard → Database → Backups → Restore (daily backup;
  loses newer data) — or "Restore to new project" to compare, but first make
  sure its cron jobs cannot run (they would send real reminders and emails).

## 6. Read-only queries used while watching

API errors in the last 15 minutes (MCP `query_logs`, window = last 15 min):

```sql
select splitByString(' | ', event_message)[2] as status,
       splitByString('?', splitByString(' | ', event_message)[3])[1] as path, count() as n
from logs where source = 'edge_logs'
  and (position(event_message, '/rest/v1/rpc/') > 0 or position(event_message, '/rest/v1/bookings') > 0)
  and toInt32OrZero(splitByString(' | ', event_message)[2]) >= 400
group by status, path order by n desc limit 20
```
