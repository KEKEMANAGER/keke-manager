Fleet on the profile: one driver, many vehicles

The driver profile asked for ONE vehicle type and ONE class. That was already
untrue the moment a driver owned a second car, and useless to a transport
company with five of them. The rest of the platform never believed it anyway:
dispatch, the job board and the local notifier all match on the `vehicles`
table, one row per car. Only this screen pretended there was a single answer —
and because the same fact was writable in two places, the two drifted apart,
which is how a registered bus came to be advertised as a sedan.

So there is no single answer on the profile any more. It shows the fleet and
edits nothing.

- components/driver/DriverVehiclesSummary.tsx (new): the driver's vehicles as a
  list on his own profile — model, type, class, plate, seats, an active dot —
  with the car count in the header and a "manage" link to the vehicle screen.
  One car is a list of one, five cars are a list of five. Rows with neither
  plate nor model are abandoned drafts and are left out, so a stray tap on
  "add vehicle" does not show up here as a phantom sedan.
- app/(driver)/profile.tsx: the two type/class pickers in edit mode and their
  read-only twins in view mode are gone; the vehicle card holds the list
  instead of the first car's model and plate. The list reloads on focus, so a
  car added on the next screen is there on the way back.
- lib/validation.ts: validateDriverProfileForm no longer demands a type/class
  pair. It used to block a driver from saving his own name or phone number
  until he had also described a car on a screen that could only hold one.
- lib/profiles.ts: driverProfileMatchesBooking now skips plateless rows, the
  same guard the push dispatch already carries — a blank draft still holds the
  form's default sedan/economy, and without this it earned a driver every
  sedan job that came through.
- src/locales ka/en/ru/hy: 7 new `profilePage` keys for the list, its empty
  state and the hint.

The `profiles.vehicle_type` / `vehicle_class` columns stay exactly where they
are, as the fallback for drivers who registered before the vehicles table did.
`syncProfileVehicle` keeps them current from the vehicle screen; this screen
now only re-saves what is already there, and skips the write entirely when
they are empty, so saving a profile no longer fails on a driver with no car.

Verified: tsc clean on the whole project; eslint clean on every changed file;
the two columns' remaining readers checked one by one — both driver-side
realtime callers pass the BOOKING's type, not the profile's, and the job board
already collected every active vehicle into `activeMatches`.
